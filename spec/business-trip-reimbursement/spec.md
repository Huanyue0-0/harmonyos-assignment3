# 功能规格：差旅报销小程序（Assignment 3）

**创建日期**：2026-10-25  
**状态**：草稿  
**输入**：用户需求描述——"帮我完成 assignment3（差旅报销小程序，HarmonyOS NEXT 6.0+，DevEco Code Agent 开发流程）"

## 概述

面向企业员工的单机差旅报销迷你应用。员工录入出差基本信息、动态增删费用明细、通过弹窗计算器计算金额、预览整单并提交，同时支持表单的本地临时保存与历史加载。

目标是让用户在 3 分钟内完成一张可提交的报销单，且在任何异常输入或存储故障下应用都不崩溃、给出可理解的中文提示。

## 用户场景与测试 *(必选)*

### 用户故事 1 - 录入基本信息与动态维护费用明细 (优先级：P1)

员工打开应用，填写出差人、部门、出差事由、起止日期等基本信息；然后在费用明细区逐条添加费用（费用类型、发生日期、金额、备注），可删除任意一条明细，列表底部实时显示费用合计。

**优先级理由**：这是报销单的核心数据，没有它后续计算器、预览和提交都无意义。

**独立测试**：仅实现本故事即可完成"填写信息 → 新增 3 条明细 → 删除 1 条 → 合计正确"这一闭环，并作为最小可用版本演示。

**验收场景**：

1. **Given** 应用首次打开，**When** 用户填写出差人与出差事由并新增一条费用明细，**Then** 明细出现在列表中且合计金额同步更新。
2. **Given** 列表已有 3 条明细，**When** 用户删除第 2 条，**Then** 列表剩余 2 条且合计重新计算。
3. **Given** 费用金额输入框为空或非法，**When** 用户尝试添加明细，**Then** 该条明细不被加入，并提示金额不合法。

---

### 用户故事 2 - 弹窗计算器计算并回填金额 (优先级：P2)

员工在填写某条费用金额时打开计算器弹窗，进行加、减、乘、除与小数运算，支持清除与退格；点击"确定"后结果自动回填到发起计算的那一条金额输入框。

**优先级理由**：金额计算是差旅报销的高频操作，也是作业的技术硬性要求。

**独立测试**：不依赖其他故事，仅验证"打开计算器 → 输入 100 ÷ 4 → 确定 → 目标金额框显示 25.00"即可交付价值。

**验收场景**：

1. **Given** 计算器显示 0，**When** 用户依次点击 1、0、0、÷、4、=，**Then** 显示 25。
2. **Given** 计算器已有结果，**When** 用户点击"确定"，**Then** 弹窗关闭且对应金额输入框被回填。
3. **Given** 用户输入 5 ÷ 0 并求值，**When** 执行运算，**Then** 弹出"除数不能为 0"的中文提示，应用不崩溃、计算器仍可继续使用。
4. **Given** 用户输入非法表达式（如 `1++2`），**When** 求值，**Then** 提示表达式非法并保留原输入。

---

### 用户故事 3 - 表单校验、预览与提交 (优先级：P3)

员工点击"预览"后，在一个弹窗中查看整张报销单（基本信息 + 全部明细 + 合计）；确认无误后点击"提交"，系统再次校验必填项与金额合法性；提交成功后清空表单并提示成功，校验失败则提示具体原因。

**优先级理由**：预览与提交是报销流程的完成动作，直接影响数据是否可信。

**独立测试**：预先载入一份完整表单 → 点击预览 → 检查弹窗内容 → 提交 → 观察表单清空与成功提示。

**验收场景**：

1. **Given** 出差事由为空，**When** 用户点击提交，**Then** 弹出"请填写出差事由"提示，表单数据保留。
2. **Given** 存在金额为 0、负数或非数字的明细，**When** 用户提交，**Then** 提示金额不合法并定位到对应明细。
3. **Given** 表单完整且金额合法，**When** 用户提交，**Then** 提示提交成功，表单恢复初始空状态。
4. **Given** 表单完整，**When** 用户点击预览，**Then** 弹窗展示全部基本信息、明细与合计，且关闭预览后表单数据不丢失。

---

### 用户故事 4 - 临时保存与历史加载 (优先级：P4)

员工可在填写过程中"临时保存"当前表单；下次打开应用或点击"加载历史"时恢复上次保存的内容。存储读写失败时给出友好提示，且不影响当前已填写数据。

**优先级理由**：差旅单填写耗时较长，临时保存能防止数据丢失，是作业要求的持久化能力。

**独立测试**：填写表单 → 临时保存 → 修改/清空 → 加载历史 → 数据恢复为保存时的内容。

**验收场景**：

1. **Given** 用户已填写部分表单，**When** 点击"临时保存"，**Then** 提示保存成功。
2. **Given** 已存在临时保存数据，**When** 用户点击"加载历史"，**Then** 表单恢复为保存时的内容。
3. **Given** 本地无历史数据，**When** 用户点击"加载历史"，**Then** 提示"暂无历史数据"，应用不崩溃。
4. **Given** 本地存储读写发生异常（如序列化失败/IO 错误），**When** 执行保存或加载，**Then** 提示存储失败并保留当前表单内容。

---

### 用户故事 5 - 横竖屏自适应 (优先级：P5)

手机旋转为横屏或竖屏时，页面布局自动重排：竖屏为单列表单，横屏为更宽的两栏/多列排布，计算器与预览弹窗始终居中且不超出安全区域。

**优先级理由**：属于作业强制适配项，影响可用性但不改变核心业务数据。

**独立测试**：同一页面分别在竖屏与横屏下截图对比，确认无遮挡、无溢出、弹窗完整可见。

**验收场景**：

1. **Given** 应用处于竖屏，**When** 旋转为横屏，**Then** 表单重新排布且所有字段与按钮可见可点。
2. **Given** 计算器/预览弹窗已打开，**When** 旋转屏幕，**Then** 弹窗仍完整显示在安全区域内。

---

### 边界情况

- 金额输入超长小数、科学计数法、全角字符、纯空格时如何处理？
- 费用明细数量很多（如 50 条）时列表是否可滚动、合计是否准确？
- 计算器连续点击运算符、连续点击小数点、除以 0、结果溢出时如何处理？
- 本地存储为空、内容损坏（非法 JSON）、字段缺失时加载行为如何？
- 横屏下键盘弹出是否遮挡当前输入框？
- 用户快速重复点击"提交"是否产生重复提交提示/重复写入？

## 需求 *(必选)*

### 功能需求

- **FR-001**：应用 MUST 提供基本信息录入，至少包含出差人、部门、出差事由、开始日期、结束日期。
- **FR-002**：出差事由 MUST 为必填项，为空时提交被拒绝并提示。
- **FR-003**：应用 MUST 支持动态新增费用明细，每条明细包含费用类型、发生日期、金额、备注。
- **FR-004**：应用 MUST 支持删除任意费用明细。
- **FR-005**：列表 MUST 实时显示所有明细金额之和（保留两位小数）。
- **FR-006**：添加明细前 MUST 校验金额为大于 0 的合法数字，不合法时拒绝添加并提示。
- **FR-007**：应用 MUST 提供弹窗计算器，支持加、减、乘、除、小数点、清除、退格与求值。
- **FR-008**：计算器 MUST 支持将结果回填到发起计算的金额输入框。
- **FR-009**：计算器 MUST 捕获除零与非法表达式，给出中文友好提示且应用不崩溃。
- **FR-010**：应用 MUST 提供预览弹窗，展示基本信息、全部费用明细与合计金额。
- **FR-011**：预览弹窗关闭后 MUST 保留原表单数据。
- **FR-012**：提交前 MUST 校验出差事由非空与所有明细金额合法；失败时 MUST 提示具体原因。
- **FR-013**：提交成功后 MUST 清空表单并提示成功。
- **FR-014**：应用 MUST 支持将当前表单临时保存到本地。
- **FR-015**：应用 MUST 支持从本地加载最近一次临时保存的表单。
- **FR-016**：无历史数据时加载 MUST 提示"暂无历史数据"而非报错崩溃。
- **FR-017**：金额转换、计算器运算、JSON 序列化/解析、明细增删 MUST 使用异常捕获处理，异常时给出友好提示。
- **FR-018**：所有可能为空的属性访问 MUST 使用可选链、空合并或空赋值等空安全手段，禁止直接访问可能为空的对象属性。
- **FR-019**：页面 MUST 使用列表组件渲染表单/明细列表，使用弹性布局完成行内排版，使用相对布局容器定位计算器与预览弹窗。
- **FR-020**：全局表单状态 MUST 跨组件共享；预览弹窗数据 MUST 与表单双向绑定；计算器内部状态 MUST 为组件局部状态。
- **FR-021**：页面 MUST 支持手机横竖屏自动适配，弹窗在两种方向下完整可见。
- **FR-022**：工程 MUST 采用顶层 `AppScope/`、`common/`、`features/`、`hvigor/`、`products/`、`screenshots/` 目录，并包含 `build-profile.json5`、`hvigorfile.ts`、`oh-package.json5`、`README.md`。
- **FR-023**：工程 MUST 附带 Agent 开发过程材料：Skill 调用 Trace 日志、JSON 格式 code_audit 审计报告、人工修复缺陷清单。
- **FR-024**：交付物 MUST 包含中文作业报告（Markdown 与 Word）、运行截图目录及符合命名规范的 ZIP 包。

### 关键实体

- **报销单（ReimbursementForm）**：一次差旅报销的完整数据，包含出差人、部门、出差事由、起止日期、费用明细集合、合计金额。
- **费用明细（ExpenseItem）**：报销单中的一条费用，包含唯一标识、费用类型、发生日期、金额、备注。
- **临时保存记录（DraftRecord）**：本地持久化的一份报销单快照及保存时间。

## 假设

- 应用为单机离线应用，无后端接口、无登录与权限体系。
- 界面文案使用中文，金额单位为人民币元，显示保留两位小数。
- 费用类型从固定选项中选择（交通、住宿、餐饮、通讯、其他），不支持用户自定义类型。
- 日期选择使用系统日期选择器，默认当天。
- 本地持久化使用设备本地键值存储，仅保存一份"最近一次临时保存"。
- 运行截图因当前环境无真机/可用模拟器，先以保证编译通过并预留 `screenshots/` 目录与截图清单，由用户在 DevEco Studio 中运行后补齐。
- ZIP 包命名先使用占位符 `Assignment3_TeamX_StudentID1_StudentID2.zip`，交付前由用户替换为真实团队号与学号。
- 目标 API 为 HarmonyOS 6.0.1（API 21），使用 Stage 模型。
